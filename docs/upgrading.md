# Upgrading

How to upgrade, and a short list of what each release changes, is in the [README](../README.md#upgrading). This page explains those changes further.

## v0.0.2

### v0.0.2: Helm values

- `helm upgrade --reuse-values` takes the values of the release it upgrades as they were, so from v0.0.1 it keeps v0.0.1's defaults, such as `nodeAgent.architectures: [amd64]` and the `2Gi` memory limit. Upgrade with `-f values.yaml` instead.
- `nodeAgent.networkPolicy.enabled` is now the top-level `networkPolicy.enabled` (default `true`). v0.0.2 still honours the old key when set, and the install notes say it is deprecated; v0.0.3 removes it. The chart refuses `networkPolicy.enabled: false` with `nodeAgent.networkPolicy.enabled: true`; `null` unsets the old key. Under `--reuse-values` from v0.0.1, the old key's v0.0.1 default, `true`, counts as unset. See [docs/node-agent.md](node-agent.md).
- `ffs controller` takes controller-runtime's `--zap-*` logging flags. The chart value `controller.logLevel` (`info` or `debug`) sets `--zap-log-level`. client-go's own verbose messages stay off.

### v0.0.2: Alert delivery

- A delivery that fails transiently is retried until 24 hours after its first attempt (was 12 attempts, about 66 minutes), still at most 15 minutes apart. The 24 hours run from each message's own first attempt, and while a target backs off only its oldest message is tried: after an outage longer than a day, the oldest message is given up and the rest arrive late, in order.
- Messages queued together go out by priority, `urgent` to `low`, then feed-stale alerts, then resolutions.
- A target holds at most 1,000 queued messages. Past that, the oldest are dropped: the delivery log shows them as `dropped`, and `ffs_notify_deliveries_total{result="dropped"}` counts them.
- Webhook, Slack, Discord and Teams messages list at most 200 items plus a count of the rest (`truncated` in the webhook payload; items may carry `truncatedOwners` and `truncatedPackages`). Stored delivery payloads are capped at 256 KiB.
- Baseline and digest summaries count findings ("40 findings in 12 workloads"): the webhook `summary` gains `findings`, and a baseline's `summary.workloads` counts only workloads with findings. A digest's title counts findings in each section, as its summary does (it counted advisories). A summary queued by v0.0.1 and sent after the upgrade has no `findings`.
- Discord alerts never mention anyone. Markdown in feed, image and advisory text is escaped in Discord and Teams messages.
- A provisional finding (an OSV match Grype has not ruled on) that Grype confirms records a transition. One at or above an AlertTarget's `immediate.minPriority` that nothing was sent for yet is alerted then (was: the digest only).

See [docs/alerts.md](alerts.md).

### v0.0.2: Alert targets

- The SSRF guard also refuses the nodes' pod CIDRs and the ranges in the new `config.alertTargets.blockedCIDRs`, unless the AlertTarget sets `allowPrivate`. The pod CIDRs are the nodes' `spec.podCIDRs`: CNIs that assign pod addresses from pools of their own (Calico IPAM, Cilium cluster-pool or multi-pool, AWS VPC CNI, Azure CNI) need those pools in `alertTargets.blockedCIDRs`. Add your Service CIDR there too when it is globally routable.
- Through an HTTPS proxy, the proxy resolves endpoints (was: the cluster first). The SSRF guard then checks only endpoints given as IP addresses, so limit what the proxy can reach.
- A target gets the resolution of every finding it was told about, whatever its filters now say: when the finding's namespace is deleted, relabelled or no longer listed, or a filter added later leaves out a cluster-level finding. At start, ffs records as resolved what v0.0.1 left open for findings in deleted namespaces, so those findings alert as reopened if they come back.

### v0.0.2: Findings

- **KEV.** An advisory is in KEV when the catalogue lists any of its aliases, not only its ID. On the first KEV sync after the upgrade, advisories whose non-canonical CVE alias is in KEV turn `urgent`, with immediate alerts and Warning Events.
- **First inventory pass.** Every workload owner now records its apiVersion, so the first inventory pass re-stores every owner once, which recomputes its findings under v0.0.2's rules: Grype precedence and the Go standard library's fixed-in version. Findings that a v0.0.1 Grype not-affected verdict hid come back as new detections, on php, node and python built from source especially, and fix versions, fix availability and priority can change once. Detected, fix-available and escalation transitions, Events and alerts follow. Recording each owner's apiVersion raises nothing by itself.
- **Custom workload kinds.** Events and OpenReports reports also cover other workload kinds, such as Argo Rollouts, OpenKruise CloneSets, Strimzi pod sets and CloudNativePG clusters.
- **Grype precedence.** Grype no longer overrides upstream-runtime (CNA) or Kubernetes verdicts on the same package: an NVD CPE match on php, node or python built from source no longer replaces the CNA's fix versions.
- **Advisories.** Advisories only Grype matches (RHEL and Amazon Linux ones, say) have titles and published dates in alerts and the web UI. A vendor advisory's several CVEs are no longer merged into one advisory; groups a v0.0.1 store merged stay merged. The Go standard library's fixed-in version is chosen per release branch, and is never below the branch installed.
- **EPSS thresholds.** A finding still takes the EPSS bump at a score of 0.1 and counts as likely exploited at 0.5. When those thresholds would lower its priority, it is ranked against 90% of them (0.09 and 0.45) instead and keeps at most its previous priority, whatever raised it: a high-severity finding ranked `high` for its exposure stays `high` after the exposure goes while its score is between 0.09 and 0.1. A score that hovers at a threshold no longer moves the priority back and forth, or creates and deletes Finding resources. See `priority.epssHigh` in [docs/configuration.md](configuration.md).
- **Transition history.** Open findings' history older than `config.retention.resolved` (default 90 days) is pruned too, keeping each finding's latest 20. Triggers are set per transition, from the existing values: a finding a rollout removed is `InventoryChange` even beside a Grype DB update; a confirmed provisional finding is `NewAdvisory` (`InventoryChange` when only a rollout confirmed it); one created or reopened by an exception change is `ExceptionExpired`; one that appears already excepted is `PriorityChange`.

### v0.0.2: Feeds

- **Grype DB updates.** Below `config.feeds.grypedb.diffMinImages` (default 1000) catalogued SBOMs (images and node groups), a new Grype database re-matches every SBOM with Grype instead of diffing the builds. From it, the diff runs in a separate process 10 nice levels below the controller (nice 10 by default), with a copy of the current build on the volume (see `persistence.size` in [docs/configuration.md](configuration.md)). `0` always diffs. The diff process gets a quarter of the controller's `GOMEMLIMIT`, and the controller lowers its own by as much while the diff runs: the two soft limits add up to the controller's limit, so raise `controller.resources.limits.memory` on large clusters. A sync, and the diff in it, may take twice `feeds.grypedb.interval`, and at least an hour.
- **Matchers.** A Grype DB update, the weekly full one included, re-runs the Grype matcher alone. The OSV, upstream and Kubernetes matchers' results follow their own feeds. The first Grype DB update after this upgrade re-runs every matcher on every SBOM once, which also brings in OSV rating changes from the week before the upgrade.
- **Feed retries and staleness.** After a restart, a feed whose last sync failed is retried on its failure backoff (1 minute, doubling, at most its interval; was: a whole interval later). A feed that has never synced is stale `staleAfter` after its first attempt, across restarts, for its Event, alerts and `ffs_feed_lag_seconds`. A sync of any feed may take twice its interval, and at least an hour.
- **OSV.** The first OSV sync after the upgrade quietly recomputes the stored hash of every cached record once: no change events, no re-match. A rating-only change to a record (a GHSA rating, an Ubuntu priority) then updates findings within the poll interval, and keeps the record's observation time, so new findings on it are not held back as provisional. The first poll also takes records listed in the hour below its watermark that the cache lacks at the listed version. A record the bucket lists but does not serve is asked for again for a day; an error for it in that time is logged and does not fail the feed's sync. Records still not served after the day, those beyond 1,000 per ecosystem and records over 4 MiB are counted in `ffs_feed_skipped_total{feed="osv"}`, with the reasons `not_found`, `missing_overflow` and `too_large`.
- **CVE List.** A delta release over 64 MiB is skipped and counted in the new metric `ffs_feed_skipped_total{feed, reason}`, which starts at 0 for each feed and reason (was: the feed stopped).

### v0.0.2: Inventory and coverage

- **Gateway API routes** in other namespaces count towards a Service's exposure when a ReferenceGrant in the Service's namespace permits them.
- **Node taints.** Nodes with a `NoSchedule` or `NoExecute` taint that `nodeAgent.tolerations` does not tolerate show `node_agent_unsupported` (was `node_agent_missing`) and no longer hold back the switch to the node agent. Its to-do mentions untolerated taints, and the API's detail names the taint and `nodeAgent.tolerations`. The chart passes `nodeAgent.tolerations` to the controller.
- **Workloads not running.** A completed or failed standalone Job whose pods are gone counts as not running, so its findings rank one level lower. A workload with no running pods is resolved at the platform its pod template pins with `kubernetes.io/arch` or `kubernetes.io/os` (was: the cluster's majority platform).
- **Image cataloguing.** An image that fills the cataloguer's scratch space on its own is quarantined for 24 hours at once (was: downloaded again). A cataloguer 400 is `unresolvable`, retried after 6 hours (was: counted towards quarantine). A tag that does not resolve, named only by workloads that are not running, is looked up again after 1, 2, 4 and then at most 6 hours (was: on every inventory flush). The node agent's catalog workers run 10 nice levels below its catalog server, at most 19 (was: at nice 10), which is the same while the server runs at nice 0.

### v0.0.2: Upgrade suggestions

- **Targets.** Suggested upgrades name the target: `nginx:1.30.7`, `nginx:1.30.6 (new digest)` for a rebuilt tag, `kubernetes v1.35.10` for the cluster. Alerts, Events, a Finding's `status.suggestion.target` (the `Suggested` column), the OpenReports property `ffs.suggestedImage`, best-fix labels, the web UI's Upgrades table and the API's upgrade `label` use this display text, which is not a pullable image reference (was: `from → to`). Findings and reports with a suggestion are rewritten once after the upgrade.
- **Upgrade choice.** A candidate must fix more `urgent`, `high` and `medium` findings than it introduces, or leave `medium` and `low` no worse, to win over a further tier. Prereleases compare numerically (`rc10` after `rc2`). After the upgrade, some workloads get a different target, announced once: an `UpgradeAvailable` Event and a digest entry.
- **Re-resolution.** A suggestion is re-resolved as soon as its findings are resolved, excepted or fall below `medium` (was: at the daily pass). Owners queued for re-resolution when ffs restarts, for a `helm upgrade`, a drain or an OOM, are resolved after the restart (was: at the next daily pass). The "upgrade applied, still affected" note stays while those findings are open.
- **Cluster and runtime advice** can say `fixed in a newer minor: v1.36`, adds its k3s or rke2 note only with a target, and drops "no upgrade path" for an unknown current version.
- **`config.upgrades.overrides` keys** are normalised like image references (`postgres` means `docker.io/library/postgres`). A malformed repository or ignore glob, or two keys naming one repository, fails the configuration load. Among overlapping globs the longest literal prefix wins (was: the alphabetically first).

### v0.0.2: Outputs and API

- **End-of-life text** uses readable product names (Alpine Linux, not alpine-linux). An upgrade suggestion's end of life is always set: `supported until <date>`, a note such as `rolling release`, or `unknown`. The API's `EOL.text` for images, nodes and the control plane carries the note, or `<product> <cycle> supported` when there is no date; the web UI shows it. CentOS Linux and CentOS Stream images and nodes get an end-of-life status: CentOS Stream images, which carry CentOS Linux's os-release ID, are told apart by version (9 and later) and by the `centos-stream-release` package. Azure Linux shows a lifecycle note; endoflife.date has no Azure Linux product.
- **Events, reports and Exceptions.** FeedStale Events repeat every 50 minutes while a feed stays stale, inside the API server's one-hour Event TTL. An invalid Exception is checked again hourly, or once its expiry comes within `config.exceptions.maxDuration`. OpenReports lists its reports at start and every 10 minutes (was: on every pass). New metric `ffs_finding_cr_name_collisions`.
- **Search API.** `/api/v1/search` returns the Control plane and Nodes pages as hits of kinds `controlplane` and `nodes`, with the cluster name as `id` (was: `workload` hits with `Cluster//<name>` and `Nodes//<name>` ids).
- **Node group links.** A link to an agentless node group that shares its name with an agent group names a member node (`<name>-nodeinfo@<node>`) and opens the group that holds that node once its agent reports. Links from v0.0.1 still work.
- **Web UI.** The explorer's EPSS signal reads "EPSS bump". The image's UI package manifests (`/usr/share/ffs/ui`) list the npm packages in the bundle, from the build's module graph (was: the lockfile's production tree).
